# Модуль тестирования (03_Testing_System)

Расширяем существующий движок тестирования, не меняя архитектуру: тот же серверный слой (`src/lib/test.functions.ts`, `test-engine.server.ts`), тот же маршрут прохождения и админ-раздел.

## Что сейчас есть
- Попытка, выборка вопросов (общие + профессиональные), перемешивание, сохранение ответов, подсчёт процента, протокол HTML.
- Ограничение по числу попыток, флаги `shuffle_*`, `lock_answer`, `show_correct_answer`, `time_limit_minutes` (в БД есть, в интерфейсе не используется).
- Банк вопросов поддерживает только один правильный ответ. Вопросов в базе пока нет (0 строк).

## Чего не хватает по спецификации
1. Типы вопросов: несколько правильных, ситуационные, развернутые, привязка практических заданий.
2. Таймер: обратный отсчёт, предупреждение, автозавершение.
3. Восстановление попытки после перезагрузки страницы.
4. Интервал между попытками и правило зачёта (лучший / последний результат).
5. Разрядная логика: соответствует разряду / более низкому / не пройден.
6. Развернутые ответы: сохранение, ручная проверка преподавателем/HR.
7. Учебный и аттестационный режим (подсветка правильного ответа только в учебном).
8. Просмотр результатов по ролям (сотрудник — свои, руководитель — подразделение, HR/админ — все).

## План работ

### 1. Миграция базы
- `questions`: `question_type` (single | multi | situational | open), `reference_answer` (эталон для развернутых), `points`.
- `test_settings`: `retry_interval_hours`, `result_rule` (best | last), `warn_before_minutes`, `mode` (learning | exam), пороги разрядов в существующем `grading_rules`.
- `test_answers`: `selected_option_ids` (массив), `text_answer`, `review_status` (auto | pending | graded), `review_score`, `reviewer_id`, `reviewed_at`; уникальность по (attempt_id, question_id) для перезаписи ответа.
- `test_attempts`: статус `awaiting_review`, поле `grade_result` (соответствует разряду / пониженный / не пройден).
- Политики: сотрудник видит свои ответы; проверяющие (teacher/hr/admin) и руководитель по подразделению — соответствующие; GRANT по правилам проекта.

### 2. Серверный слой (расширение существующих функций)
- `startAttempt`: возврат незавершённой попытки вместо новой (восстановление), проверка интервала между попытками, отсутствие дублей вопросов внутри попытки, отдача типа вопроса, режима и предупреждения таймера.
- `submitAnswer`: приём массива вариантов и текста, upsert по (attempt_id, question_id), для `open` — без автозачёта (`review_status = pending`), обратная связь о правильности только в учебном режиме.
- `finishAttempt`: подсчёт с учётом мультивыбора, автозавершение по таймауту, статус `awaiting_review` при наличии развернутых ответов, расчёт разряда по порогам, применение правила best/last.
- Новые функции: `resumeAttempt`, `listPendingReviews`, `gradeOpenAnswer` (teacher/hr/admin), `listAttempts` по ролевому контуру.
- Протокол дополняется режимом, разрядным итогом и развернутыми ответами (правильные ответы — только если разрешено настройками).

### 3. Интерфейс прохождения (`/test/$professionId`)
- Экран старта: количество вопросов, лимит времени, проходной балл, номер попытки, оставшиеся попытки.
- Таймер с предупреждением и автозавершением; восстановление незавершённой попытки при перезагрузке.
- Рендер по типу вопроса: радио, чекбоксы, ситуационный, textarea для развернутого.
- Учебный режим — зелёная/красная подсветка и пояснение; аттестационный — без раскрытия.
- Индикатор прогресса, блокировка изменения ответа при `lock_answer`.

### 4. Результаты и проверка
- Страница результата: процент, статус, разряд, номер попытки, ссылка на протокол; пометка «на проверке» для развернутых ответов.
- Новый раздел `/admin/reviews`: очередь развернутых ответов, эталон, выставление балла, пересчёт итога попытки, запись в журнал действий.
- Раздел `/admin/tests`: редактирование типа вопроса, нескольких правильных вариантов, эталонного ответа и новых настроек теста.

### 5. Данные
Наполнение банка вопросами не входит в задачу — вопросы вносятся через админ-панель. Если нужен стартовый набор для проверки, добавлю его отдельной миграцией.

## Технические детали
- Всё через `createServerFn` + `requireSupabaseAuth`; правильные ответы не уходят на клиент вне разрешённого режима.
- Существующие маршруты и компоненты не переписываются, только расширяются.
- Типы базы перегенерируются после миграции, код правится после неё.
