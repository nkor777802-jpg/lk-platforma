# План: делегирование выдачи ролей

## Подтверждённое текущее состояние

- Роли хранятся в `public.user_roles`, один пользователь может иметь несколько ролей.
- Сейчас в `/admin/users` роль меняется через одиночный `Select` в колонке «Роль». При выборе серверная функция `setUserRoles` удаляет все текущие роли пользователя и вставляет одну выбранную.
- Право `admin` может выдать только `admin` (проверка уже есть в `setUserRoles`).
- Просмотр раздела «Пользователи» доступен ролям `admin`, `hr`, `manager`.
- Список пользователей (`listAdminUsers`) отдаёт все профили через `supabaseAdmin`, без скоупинга по подразделениям для руководителя.

## Что будем делать

1. **Центральная матрица делегирования ролей**
   - Создать `src/lib/roles.ts` с константами:
     - `ROLE_HIERARCHY`: admin → hr/teacher/manager → employee.
     - `ASSIGNABLE_ROLES: Record<AppRole, AppRole[]>` — какие роли может назначать/снимать каждый исполнитель.
   - Пример матрицы (можно скорректировать перед стартом):
     - `admin` → все роли.
     - `hr` → `employee`, `manager`, `teacher`.
     - `manager` → только `employee`.
     - `teacher` → не может назначать роли (нет доступа к `/admin/users`).

2. **Серверная валидация `setUserRoles`**
   - Проверить, что исполнитель имеет право менять роли.
   - Для каждой роли в `data.roles` убедиться, что она входит в `ASSIGNABLE_ROLES[actorRole]`.
   - Запретить снятие собственной роли `admin`, если это последний администратор.
   - Сохранить аудит-запись через `logAction`.

3. **Создание пользователя с учётом делегирования**
   - В `createAdminUser` заменить поле `role: single` на `roles: AppRole[]`.
   - Применить ту же матрицу `ASSIGNABLE_ROLES`.
   - `employee` добавлять не нужно (она назначается автоматически триггером `handle_new_user`), остальные роли записывать в `user_roles`.

4. **UI: мульти-ролевой редактор в `/admin/users`**
   - Заменить одиночный `Select` в колонке «Роль» на мульти-селект (чекбоксы в `Popover`/`Command` или `SelectContent` с чекбоксами).
   - Показывать только роли, доступные текущему администратору/HR/руководителю.
   - Роли, которые пользователь уже имеет, но исполнитель не может их менять, отображать как read-only бейджи.
   - В таблице по-прежнему показывать «основную» роль по приоритету `admin > hr > teacher > manager > employee`.

5. **Скоупинг списка пользователей для `manager`**
   - В `listAdminUsers` для роли `manager` возвращать только подчинённых (`manages_user`) и сотрудников своего подразделения.
   - Для `admin`/`hr` оставить полный список.

6. **Безопасность и проверки**
   - Никаких изменений схемы БД не требуется.
   - Все проверки выполняются на сервере в `createServerFn`; UI лишь ограничивает видимость опций.
   - После правок запустить `bun run build` и проверить `/admin/users` от имени `admin`, `hr` и `manager`.

## Что НЕ входит в план

- Изменение enum `app_role` или таблицы `user_roles`.
- Новые страницы/разделы.
- Автоматическое назначение ролей по домену email.
